# All input goes through the Board

The app never creates input in software: every key press, hold, click, pointer move and camera drag it sends to the game goes to the Board (or only to the log in a dry run). The player wants no software-generated input inside the game at all, so there is deliberately no `SendInput` fallback when the Board is missing or fails; a run refuses to start or halts instead. `fishing.Input` is the one port the cycle sends input through, its live implementation is the Guard over the Board, and a test fails the build if the module calls a Windows input-writing API (`SendInput`, `keybd_event`, `mouse_event`, `SetCursorPos`, `SetPhysicalCursorPos`, `PostMessage`, `BlockInput`). Reading input state (pointer position, key state, the key hook the board check uses) is not input and stays allowed. The one input outside `fishing.Input` is the board check, which taps a test key (swallowed by the key hook) and nudges the pointer to prove the Board reaches Windows; it still goes through the Board, needs no game window, and is refused while a run goes.
